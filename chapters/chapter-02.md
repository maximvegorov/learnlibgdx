Продолжим работу с проектом `my-game`. Все изменения этой главы относятся к модулю `core`; настольный запуск по-прежнему создаёт `new MyGame()`. ## Жизненный цикл приложения

### Кто управляет приложением

В `Lwjgl3Launcher` мы передали объект `MyGame` бэкенду. Дальше LibGDX вызывает методы этого объекта при запуске, подготовке кадров, изменении размера окна и завершении приложения. Набор таких событий называют **жизненным циклом**.

Его описывает интерфейс `ApplicationListener`. Класс `ApplicationAdapter`, использованный в первой главе, предоставляет пустые реализации всех его методов. Поэтому можно переопределять только нужные.

| Метод | Назначение |
| --- | --- |
| `create()` | Первоначальная настройка; вызывается один раз при создании приложения |
| `resize(int width, int height)` | Обработка размеров области отображения; вызывается после `create()` и при изменении размеров |
| `render()` | Подготовка очередного кадра: обычно обновление игры и отрисовка |
| `pause()` | Обработка приостановки приложения и подготовка к завершению |
| `resume()` | Обработка возвращения из приостановленного состояния |
| `dispose()` | Освобождение ресурсов при завершении приложения |

Порядок вызовов и назначение методов приведены в [документации жизненного цикла libGDX](https://libgdx.com/wiki/app/the-life-cycle). Для обычного запуска и закрытия окна последовательность можно представить так:

```text
create() → resize(...) → render() → render() → ... → pause() → dispose()
```

Во время работы возможны дополнительные вызовы `resize()`, а также приостановка и возобновление.

В LWJGL3 по умолчанию сворачивание окна приостанавливает приложение, а потеря фокуса — нет. Это поведение настраивают `setPauseWhenMinimized(...)` и `setPauseWhenLostFocus(...)` в конфигурации запуска. Поэтому переход в другое окно сам по себе не следует считать гарантированным вызовом `pause()`. См. [настройки LWJGL3](https://github.com/libgdx/libgdx/blob/master/backends/gdx-backend-lwjgl3/src/com/badlogic/gdx/backends/lwjgl3/Lwjgl3ApplicationConfiguration.java).

### Наблюдаем вызовы

Временно замените содержимое `MyGame.java` следующим кодом. Путь к файлу в проекте из первой главы: `core/src/main/java/ru/learnlibgdx/mygame/MyGame.java`.

```java
package ru.learnlibgdx.mygame;

import com.badlogic.gdx.ApplicationAdapter;
import com.badlogic.gdx.Gdx;
import com.badlogic.gdx.graphics.GL20;

public class MyGame extends ApplicationAdapter {
    private boolean firstFrame = true;

    @Override
    public void create() {
        Gdx.app.log("Lifecycle", "create");
    }

    @Override
    public void resize(int width, int height) {
        Gdx.app.log("Lifecycle", "resize: " + width + " x " + height);
    }

    @Override
    public void render() {
        if (firstFrame) {
            Gdx.app.log("Lifecycle", "first render");
            firstFrame = false;
        }

        Gdx.gl.glClearColor(0.10f, 0.15f, 0.25f, 1.0f);
        Gdx.gl.glClear(GL20.GL_COLOR_BUFFER_BIT);
    }

    @Override
    public void pause() {
        Gdx.app.log("Lifecycle", "pause");
    }

    @Override
    public void resume() {
        Gdx.app.log("Lifecycle", "resume");
    }

    @Override
    public void dispose() {
        Gdx.app.log("Lifecycle", "dispose");
    }
}
```

Запустите `./gradlew lwjgl3:run` из каталога приложения, измените размер окна, сверните его, восстановите и закройте. В Windows используйте `.\gradlew.bat lwjgl3:run`. Сравните сообщения в консоли с действиями. Мы выводим сообщение только для первого кадра, чтобы частые вызовы `render()` не заполняли журнал.

В дальнейшем создавайте графические ресурсы в `create()` или в последующих вызовах жизненного цикла, когда бэкенд уже подготовил графический контекст. Такие операции должны выполняться в потоке отрисовки, как объясняет [руководство по потокам libGDX](https://libgdx.com/wiki/app/threading). Конструктор главного класса вызывается ещё до передачи объекта бэкенду, поэтому обращаться там к `Gdx.gl` нельзя.

### Кто освобождает ресурсы

У таких объектов, как `Texture` и `SpriteBatch`, есть ресурсы вне Java-кучи. Сборщик мусора Java не заменяет вызов их `dispose()`. Когда объект больше не нужен, его владелец должен освободить эти ресурсы. Это правило описано в [руководстве по управлению памятью libGDX](https://libgdx.com/wiki/articles/memory-management).

Пока мы только очищаем цветовой буфер и не создаём подобных объектов, освобождать в примере нечего. Позже поместим соответствующие вызовы в `dispose()` игры или экрана, который владеет ресурсами. Приостановка приложения не означает, что все ресурсы нужно немедленно уничтожить: игра может продолжиться.

## Обновление, отрисовка и дельта

### Что происходит за один кадр

Внутри кадра удобно выделить три действия:

1. Прочитать ввод: например, проверить нажатие клавиши.
2. Обновить состояние: изменить координаты, таймеры и другие игровые данные.
3. Нарисовать кадр по текущему состоянию.

По умолчанию LibGDX вызывает `render()` непрерывно. Частота зависит от оборудования и настроек; библиотека также поддерживает отрисовку по запросу, но в этой главе оставляем обычный режим. См. [режимы отрисовки](https://libgdx.com/wiki/graphics/continuous-and-non-continuous-rendering).

Отдельного обязательного метода `update()` в `ApplicationListener` нет. Его можно написать самостоятельно и вызывать из `render()`. Следующий фрагмент показывает устройство такого метода; это схема, а не полная замена класса:

```java
@Override
public void render() {
    float delta = Gdx.graphics.getDeltaTime();
    handleInput();
    update(delta);
    draw();
}
```

Методы `handleInput()`, `update()` и `draw()` определяем мы сами. Разделение помогает проверить игровую логику без чтения команд рисования. Не добавляйте в `render()` бесконечный `while` или ожидание через `Thread.sleep()`: метод должен выполнить работу одного кадра и вернуть управление бэкенду.

### Зачем нужна дельта

**Дельта времени**, или `delta`, — промежуток между текущим и предыдущим кадром в секундах. Его возвращает `Gdx.graphics.getDeltaTime()`. Не путайте секунды с миллисекундами. Назначение метода закреплено в [интерфейсе Graphics](https://github.com/libgdx/libgdx/blob/master/gdx/src/com/badlogic/gdx/Graphics.java).

Предположим, объект должен двигаться со скоростью 120 единиц в секунду. Запись `x += 2f` означает перемещение на две единицы **за кадр**: при 60 кадрах в секунду получится 120 единиц за секунду, а при 144 — уже 288. Для скорости в единицах за секунду используйте:

```java
x += speed * delta;
```

Здесь `x` — координата, а `speed` — скорость. Проверим расчёт при равномерной частоте кадров:

| Частота | Дельта, секунд | Перемещение за кадр при `speed = 120f` | Перемещение за секунду |
| --- | --- | --- | --- |
| 30 FPS | `1 / 30 ≈ 0.0333` | 4 | 120 |
| 60 FPS | `1 / 60 ≈ 0.0167` | 2 | 120 |
| 120 FPS | `1 / 120 ≈ 0.0083` | 1 | 120 |

FPS — количество кадров в секунду. Для равномерного движения с постоянной скоростью умножение на дельту сохраняет пройденное расстояние за одинаковое время, с учётом погрешности чисел с плавающей точкой. Таймер обновляется похожим образом: `elapsed += delta`.

### Большая дельта и шаг обновления

После задержки кадра дельта может оказаться большой. Если за один шаг объект переместится далеко, простая проверка столкновения только в конечной позиции может пропустить препятствие.

В учебном примере ниже ограничим шаг обновления:

```java
float step = Math.min(delta, 0.1f);
update(step);
```

Это выбранное нами ограничение: за один кадр модель продвинется максимум на одну десятую секунды. Оно уменьшает скачки анимации, но отбрасывает часть прошедшего времени. Если задержки повторяются, игровое время будет идти медленнее реального. Поэтому такой таймер не подходит для измерения точного времени сеанса.

Другой подход — фиксированный шаг: накапливать прошедшее время и выполнять обновления одинаковой длительности, например по `1f / 60f` секунды. За один кадр тогда может пройти несколько обновлений. Для устойчивой физики этот подход требует отдельного разбора, включая ограничение количества шагов и интерполяцию изображения. Одно умножение на `delta` не делает любую симуляцию независимой от частоты кадров.

## Game, Screen и переключение экранов

### Разделяем ответственность

Когда появляются меню, игровой процесс и настройки, держать всё в одном `render()` неудобно. LibGDX предоставляет класс `Game`, реализующий `ApplicationListener`, и интерфейс `Screen` для отдельных экранов.

`Game` хранит текущий экран и передаёт ему вызовы `render`, `resize`, `pause` и `resume`. В `Screen.render(float delta)` дельта уже приходит аргументом. Такое перенаправление видно в [реализации Game](https://github.com/libgdx/libgdx/blob/master/gdx/src/com/badlogic/gdx/Game.java).

Экран — это часть приложения, например главное меню, а не отдельное окно операционной системы. У `Screen` есть следующие методы:

| Метод | Роль |
| --- | --- |
| `show()` | Экран становится текущим |
| `render(float delta)` | Экран обновляет состояние и рисует кадр |
| `resize(int width, int height)` | Экран получает актуальные размеры |
| `pause()` и `resume()` | Экран обрабатывает приостановку и возобновление приложения |
| `hide()` | Экран перестаёт быть текущим |
| `dispose()` | Экран освобождает свои ресурсы |

У экрана нет метода `create()`, а `show()` может вызываться неоднократно. Эти события описаны в [интерфейсе Screen](https://github.com/libgdx/libgdx/blob/master/gdx/src/com/badlogic/gdx/Screen.java). Для примера будем наследовать [ScreenAdapter](https://github.com/libgdx/libgdx/blob/master/gdx/src/com/badlogic/gdx/ScreenAdapter.java): он предоставляет пустые реализации, позволяя переопределить нужные методы.

### Главный класс игры

Теперь замените диагностический `MyGame` этим окончательным вариантом. В том же пакете создайте ещё два файла, `MenuScreen.java` и `PlayScreen.java`, приведённые ниже.

```java
package ru.learnlibgdx.mygame;

import com.badlogic.gdx.Game;

public class MyGame extends Game {
    private MenuScreen menuScreen;
    private PlayScreen playScreen;

    @Override
    public void create() {
        menuScreen = new MenuScreen(this);
        playScreen = new PlayScreen(this);
        showMenu();
    }

    public void showMenu() {
        setScreen(menuScreen);
    }

    public void showPlay() {
        setScreen(playScreen);
    }

    @Override
    public void dispose() {
        super.dispose();
        menuScreen.dispose();
        playScreen.dispose();
    }
}
```

Оба экрана создаются один раз и хранятся в игре. Поэтому возврат к игровому экрану сохранит его поля. В этом примере вход из меню означает продолжение, а не начало новой партии.

Метод `render()` в `MyGame` не переопределяем: унаследованный вариант передаёт кадр текущему экрану. Если позже понадобится собственный `render()`, сохраните в нём вызов `super.render()`, иначе этот механизм перестанет работать.

### Экран меню

Содержимое `MenuScreen.java`:

```java
package ru.learnlibgdx.mygame;

import com.badlogic.gdx.Gdx;
import com.badlogic.gdx.Input;
import com.badlogic.gdx.ScreenAdapter;
import com.badlogic.gdx.graphics.GL20;

public class MenuScreen extends ScreenAdapter {
    private final MyGame game;

    public MenuScreen(MyGame game) {
        this.game = game;
    }

    @Override
    public void show() {
        Gdx.app.log("Menu", "Enter: open game");
    }

    @Override
    public void render(float delta) {
        Gdx.gl.glClearColor(0.10f, 0.15f, 0.25f, 1.0f);
        Gdx.gl.glClear(GL20.GL_COLOR_BUFFER_BIT);

        if (Gdx.input.isKeyJustPressed(Input.Keys.ENTER)) {
            game.showPlay();
            return;
        }
    }
}
```

Переданная ссылка `game` позволяет запросить переход. `isKeyJustPressed()` проверяет новое нажатие, тогда как `isKeyPressed()` проверяет удержание клавиши. Для переключения режима по одному нажатию используем первый метод. См. [API ввода](https://github.com/libgdx/libgdx/blob/master/gdx/src/com/badlogic/gdx/Input.java).

Меню пока обозначено синим фоном, а подсказка выводится в консоль. Текст и кнопки в окне добавим при изучении интерфейса.

### Игровой экран

Содержимое `PlayScreen.java`:

```java
package ru.learnlibgdx.mygame;

import com.badlogic.gdx.Gdx;
import com.badlogic.gdx.Input;
import com.badlogic.gdx.ScreenAdapter;
import com.badlogic.gdx.graphics.GL20;

public class PlayScreen extends ScreenAdapter {
    private final MyGame game;
    private float elapsed;
    private boolean paused;

    public PlayScreen(MyGame game) {
        this.game = game;
    }

    @Override
    public void show() {
        Gdx.app.log("Play", "Space: pause/resume, Escape: menu");
    }

    @Override
    public void render(float delta) {
        if (Gdx.input.isKeyJustPressed(Input.Keys.SPACE)) {
            paused = !paused;
            Gdx.app.log("Play", "paused: " + paused);
        }

        if (!paused) {
            update(Math.min(delta, 0.1f));
        }
        draw();

        if (Gdx.input.isKeyJustPressed(Input.Keys.ESCAPE)) {
            game.showMenu();
            return;
        }
    }

    private void update(float delta) {
        elapsed += delta;
    }

    private void draw() {
        float green = 0.35f + 0.15f * (float) Math.sin(elapsed);
        Gdx.gl.glClearColor(0.08f, green, 0.12f, 1.0f);
        Gdx.gl.glClear(GL20.GL_COLOR_BUFFER_BIT);
    }

    @Override
    public void pause() {
        paused = true;
    }
}
```

`elapsed` хранит накопленное игровое время в секундах. Синус меняется от −1 до 1, поэтому зелёная компонента плавно колеблется от `0.20` до `0.50`. При выбранной формуле полный цикл занимает примерно `2π` секунд игрового времени. `draw()` читает состояние, а его изменение происходит в `update()`.

Пробел переключает **игровую паузу**, которую мы реализовали полем `paused`. Во время неё приложение продолжает получать кадры, читать ввод и рисовать, но не увеличивает `elapsed`.

Метод жизненного цикла `pause()` тоже устанавливает этот флаг. Мы намеренно не сбрасываем его в `resume()`: после восстановления свёрнутого окна игрок продолжает игру пробелом. Это решение нашего примера. Сам `ScreenAdapter` не реализует игровую паузу.

### Что делает переключение

При вызове `setScreen(nextScreen)` происходит следующая последовательность:

1. У старого экрана, если он есть, вызывается `hide()`.
2. Новый экран становится текущим.
3. У нового экрана вызывается `show()`.
4. Затем он получает `resize()` с текущими размерами.

Эти вызовы выполняются внутри `setScreen()`. Отрисовка нового экрана начнётся при следующем вызове `Game.render()`. Сам переход не прерывает Java-метод старого экрана, поэтому после него в примерах стоит `return`. Переход размещён после рисования: текущий кадр уже очищен, а следующий нарисует выбранный экран. Порядок можно проверить в [исходном коде Game](https://github.com/libgdx/libgdx/blob/master/gdx/src/com/badlogic/gdx/Game.java).

`hide()` не вызывает `dispose()`. Даже стандартный `Game.dispose()` только скрывает текущий экран. Поэтому наш `MyGame.dispose()` сначала вызывает `super.dispose()`, а затем явно освобождает **оба** сохранённых экрана.

Сейчас их `dispose()` унаследован от `ScreenAdapter` и ничего не делает. Когда у экранов появятся собственные ресурсы, переопределим этот метод. Не освобождайте такие ресурсы в `hide()`, если собираетесь повторно использовать тот же экран без их восстановления. Общие ресурсы, которыми владеет игра, следует освобождать в игре, а не по одному разу в каждом экране.

### Проверяем результат

Соберите проект командой `./gradlew build`, затем запустите `./gradlew lwjgl3:run`. В Windows используйте соответствующие команды с `.\gradlew.bat`.

1. При запуске должен появиться синий фон меню и подсказка в консоли.
2. Нажмите Enter. Фон станет зелёным и начнёт плавно менять яркость.
3. Нажмите пробел: цвет перестанет меняться. Повторное нажатие продолжит анимацию.
4. Нажмите Escape, чтобы вернуться в меню, затем Enter для возврата в игру. Поля `elapsed` и `paused` сохранятся; время, проведённое в меню, не прибавится к игровому таймеру.
5. Сверните и восстановите окно во время игры. При стандартной настройке LWJGL3 анимация останется на паузе до нажатия пробела.

Для самостоятельной работы добавьте в `PlayScreen` метод `reset()`, который присваивает `elapsed = 0f` и `paused = false`. Вызовите его в `showPlay()` перед `setScreen(playScreen)`. Проверьте, что теперь каждый переход из меню начинает анимацию заново, и объясните, почему для этого не понадобилось создавать новый объект экрана.
